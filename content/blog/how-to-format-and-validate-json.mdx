In this guide, you'll learn how to format and validate JSON properly, the most common syntax errors that break payloads, and a few habits that will save you hours of debugging.

## What Is JSON Formatting (and Why Does It Matter)?

JSON (JavaScript Object Notation) is a text-based data format. Machines don't care whether it's minified onto one line or neatly indented — but **humans do**.

**Formatting** (also called *pretty-printing* or *beautifying*) means adding consistent indentation and line breaks so the structure is visible at a glance:

```json
{
  "user": {
    "id": 42,
    "name": "Ada Lovelace",
    "roles": ["admin", "editor"]
  }
}
```

Compare that to:

```json
{"user":{"id":42,"name":"Ada Lovelace","roles":["admin","editor"]}}
```

Same data. Wildly different readability. When you're debugging a failing API response at 2 AM, formatted JSON is the difference between spotting the problem in seconds and spending twenty minutes counting braces.

## The 5 Most Common JSON Syntax Errors

JSON is strict — far stricter than JavaScript object literals. These five mistakes cause the vast majority of "invalid JSON" errors:

### 1. Trailing Commas

```json
{ "name": "Ada", }
```

JavaScript tolerates this. JSON does not. The last item in an object or array must **not** be followed by a comma.

### 2. Single Quotes

```json
{ 'name': 'Ada' }
```

JSON strings and keys **must** use double quotes. This is the most common error when copying objects out of JavaScript or Python code.

### 3. Unquoted Keys

```json
{ name: "Ada" }
```

Every key in JSON must be a double-quoted string. No exceptions.

### 4. Comments

```json
{
  // TODO: remove this
  "name": "Ada"
}
```

Standard JSON has **no comment syntax**. If you need comments in config files, use JSONC or JSON5 — but never send commented JSON to an API.

### 5. Undefined, NaN, and Infinity

```json
{ "score": NaN }
```

These are valid JavaScript values but **not valid JSON**. Use `null` or a number instead.

## Formatting vs Validating — Two Different Jobs

People often use these terms interchangeably, but they solve different problems:

| Task | What it does | When you need it |
|---|---|---|
| Formatting | Re-indents valid JSON for readability | Reading logs, reviewing API responses |
| Validating | Checks whether text is syntactically correct JSON | Before sending a payload, debugging parse errors |
| Minifying | Removes all whitespace to shrink size | Production payloads, embedding in URLs |

A good workflow uses all three: **validate** to confirm correctness, **format** to read and debug, **minify** to ship.

## Debugging a Broken Payload: A Systematic Approach

When JSON.parse throws and the payload is huge, don't hunt randomly. Work through this checklist:

1. **Validate first.** Paste the payload into a validator — it will report the exact line and column of the first error.
2. **Fix only the first error.** Parsers stop at the first problem; re-validate after each fix instead of fixing everything at once.
3. **Check the copy-paste boundaries.** Truncated payloads (missing closing braces) are the #1 cause of errors in copied API responses.
4. **Watch for smart quotes.** Text copied from Word, Slack, or Notion often contains `"curly quotes"` instead of `"straight quotes"`.
5. **Check encoding.** A stray BOM or non-breaking space at the start of a file can break strict parsers.

## Frequently Asked Questions

### Is formatting JSON lossy?

No. Pretty-printing only adds whitespace, which JSON parsers ignore. The data is identical before and after.

### What's the difference between JSON and a JavaScript object?

JSON is a **text format** with strict rules: double quotes only, no comments, no trailing commas, no functions. A JavaScript object literal is code and follows JavaScript's looser rules.

### Can JSON contain duplicate keys?

The spec allows it, but behavior is undefined — most parsers silently keep the last value. Avoid duplicates; they're almost always a bug.

### How do I handle dates in JSON?

JSON has no date type. The convention is an ISO 8601 string like `"2026-08-17T10:30:00Z"`, which every language can parse reliably.
